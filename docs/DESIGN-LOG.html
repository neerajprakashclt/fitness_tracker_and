Fitness Tracker for Android: Design and Build Log

A native, standalone, personal-use port of the Python Fitness Tracker. Target: Pixel 7, Android 17+, sideloaded. This page is appended to as each stage is built: what was designed, what went wrong, how it was fixed.

Overview

The PC app is a FastAPI + SQLite web app. It imports FIT/GPX/TCX files, derives per-activity summaries, and computes training analytics. The Android app does the same on the phone, with no server and no account. The PC app is the reference: where the two disagree about how something is calculated, the PC code is right.

Full feature inventory and porting analysis: docs/FEATURE-ANALYSIS.md (13 sections). This page records the design as it is realised and the problems met on the way.

Architecture

LayerChoiceWhy
:corePure Kotlin/JVM: parsers, analytics, formattingAll ported logic lives here and is unit-tested on the JVM against golden fixtures made by the PC code.
:dataRoom (SQLite), DAOs, repositories, raw-file archive, WorkManagerSchema mirrors the PC; identity is file_hash so a later sync is a mapping exercise.
:appJetpack Compose, Material 3, Navigation Compose, ViewModelsNo logic in composables.
Charts / mapsVico / MapLibre Native (OSM raster tiles)Both proven in phase 0 on real data (activity charts with scrubber, stacked columns, duration curve, 140,886-point heatmap).
Stream storageGzipped JSON files in filesDir/streams/<file_hash>.json.gzAndroid reads database rows through a ~2 MB window (measured: 2,000 KB ok, 2,200 KB fails); files have no limit.

Two-layer analytics (carried over from the PC app)

Layer 1: per-activity summaries computed once from streams, stored, and versioned (metrics, best efforts, simplified routes, places). Layer 2: cheap query-time analytics over Layer 1 (curves, zones, log, critical speed, run types, load safety, volume, route matching). Changing a threshold re-runs only the scoring over stored summaries, never the streams.

Verification approach

The PC code generates "golden" JSON for real and synthetic files; the Kotlin port must reproduce it (exact for integers and strings, tolerance for floats). Every PC constant is exported too, so drift is a failing test.

UI and themes

Direction (2026-10-17): look and behave like Strava, with a theme switcher in Settings > Appearance offering a Strava theme, an iOS-style theme, and several Unix/terminal themes. The choice is stored on the device and applies to every screen, chart and map.

Strava-style layout

  • Bottom bar: Activities (feed), Fitness, Log, Running, More. (Strava's Record and Groups tabs do not apply: this app imports files and has no social features.)
  • Feed card: sport icon, auto title ("Morning Run"), date and place (from the offline places feature), a stats row (distance, pace, time), and a route thumbnail drawn from the stored polyline on a plain canvas, so the feed makes no tile requests.
  • Activity detail: route map header, big stat grid, splits table with proportional pace bars, stacked charts with the scrubber, zones, best efforts on this run.
  • You / Log: this week summary with a bar chart, calendar, year-over-year, goals with progress rings.

Open design questions (decide in phase 1)

  • iOS fidelity: a hand-made iOS-style component set (more control, no dependency) versus a Cupertino-style Compose library (faster, one more dependency; to be evaluated for Android 17 and this Compose version). The system font on Android is not San Francisco, which cannot be bundled; the iOS theme uses the system sans with iOS spacing, weights and layout.
  • Monospace font: the system monospace, or one bundled open-licence font (small file) for a consistent terminal look.
  • Light variants for the Unix themes (Solarized and Gruvbox both have them) and a "follow system" mode.

Build log

Newest entries are added at the bottom of this section.

Stage A: research 2026-10-17

Read the PC app's source (schema, API, importers, every analytics module, front-end pages) and measured its database. Compared with the existing Android guide and wrote docs/FEATURE-ANALYSIS.md.

Result: the Android guide covered about half of the PC's current functionality. Decisions taken afterwards: target is a Pixel 7 on Android 17+; all optional extras (poster, cities, terrain elevation, Strava CSV elevation) are wanted; the 14-year history is moved by importing the raw archive on the phone.

Issue A1: the Android guide had drifted from the PC app

Symptom
The guide defined duration as timer seconds; the PC app now stores moving time. Goals, TCX and duplicate detection were missing.
Cause
The guide was written 2026-09-30; the PC app has had two roadmaps since.
Solution
Corrected CLAUDE.md; added the missing tables and features; analysis records the drift in section 3.4.

Stage B: staging the 14-year history 2026-10-17

Copied the PC's raw archive to FitnessTrackerAndroid/seed/ (gitignored): 3,265 files (120 MB), Strava's activities.csv, and pc-side-data.json holding 406 elevation overrides and 8 terrain-elevation profiles keyed by file_hash. The overrides and terrain values exist only in the PC database, not in the raw files, so exporting them prevents silently losing elevation for the Amazfit activities.

Issue B1: no phone connected for the transfer

Symptom
adb devices listed nothing.
Cause
USB debugging not enabled or no device attached.
Status
Open. The seed is staged; push with adb push once the Pixel 7 is connected (commands in CLAUDE.md).

Stage C: golden-fixture exporter 2026-10-17

tools/export_golden.py (PC repo) runs the PC code over a chosen set of files and writes seed/golden/golden.json, constants.json and the input files. Contents:

  • per_file: parse summary, per-stream statistics (count, sum, min, max, first/last five), Layer 1 metrics, best efforts, simplified route polylines, load under fixed settings, km and mile splits.
  • mini_history: every Layer 2 analytic over a temporary database holding only the chosen files, with "today" pinned to 2026-10-17.
  • full_history (--full): the same analytics over a copy of the real database, as an end-to-end oracle (1,261 runs classified).
  • constants.json: every named constant in the analytics and importer modules.

Selection: 74 real files spread over format, sport and source, with edge cases (activities with power data, no sport recorded, walks whose moving time is far below elapsed time) plus 3 synthetic FIT files (cycling with 25 minutes of power, a run with a 200 s stop, an indoor run with no GPS). Output is 3 MB of JSON, produced in about 30 seconds.

Issue C1: the edge cases were silently cut off by the file cap

Symptom
First run: 60 files chosen, but none had power data and the "walk" and "no sport" edge cases were absent.
Cause
Edge cases were added after the group picks, then the list was trimmed to the cap from the end, which removed exactly the edge cases.
Solution
Add edge cases first, then groups; raise the default cap to 80. A summary check after each run now lists which edge cases landed.

Issue C2: the only "power" files in the history are running power, not cycling

Symptom
The two files with a 20-minute power value were runs; their load is scored from heart rate, so the cycling TSS path had no real example.
Cause
The user's history has almost no cycling with a power meter; load only uses power for cycling and e-biking.
Solution
Generate a synthetic cycling FIT with 25 min at 250 W using the PC test helper. Result: method power, load 41.67, normalized power 250. Relabelled the real files "has power data".

Issue C3: tooling quirks while building the exporter

Symptom
The Git Bash shell lacked uname and touch (venv activation failed); a scripted edit piped into Python did not apply and the first re-run silently produced the same output; a recursive delete of the output folder was blocked.
Cause
Stripped-down shell environment; PowerShell here-string piping to python - did not run the script; the delete was refused by a path-safety rule.
Solution
Use PowerShell with the venv's python.exe directly; make code edits with the editor tool and then confirm by searching the file; clear the output folder with shutil.rmtree on the exact path. Lesson: verify an edit landed before trusting a re-run.

Findings from the fixtures that affect the Kotlin port 2026-10-17

Finding C4: unknown FIT sports are stored as bare numbers

Observation
One real FIT file is stored with sport "62". fitparse yields the raw number when it does not know the enum value, and the PC stores its string form.
Consequence
The Garmin FIT SDK may name or number such sports differently, so sport strings will differ between the apps for exotic sports.
Plan
In the FIT spike, compare sport strings for every distinct sport in the fixtures; map the SDK's value to the PC's string (number as text when unnamed). Parity test on parsed.sport.

Finding C5: day bucketing depends on the machine's time zone

Observation
The PC buckets days in the machine's zone; this machine is US Eastern. The fixtures record that.
Consequence
The Kotlin tests must run with the default zone set to America/New_York or daily load and weekly totals will not match. On the phone, the device zone is used, as on the PC.

Finding C6: daily_load is extended to the real "today"

Observation
The PC pads daily_load through the current date, which cannot be pinned from outside.
Solution
The fixtures keep rows only up to the last activity day. Kotlin tests compare that range; the extension to today is tested separately with an injected clock.

Phase 0: scaffold and spikes 2026-10-17

Goal: remove the biggest unknowns before building. The project now has three modules (:core pure Kotlin, :data Room, :app Compose), a Gradle wrapper, and a throwaway spike app that runs on a Pixel 7 class emulator (Android 17, API 37). Every spike used the user's real data exported from the PC app.

Toolchain (looked up on 2026-10-17, not guessed): Gradle 9.8.1, Android Gradle Plugin 9.4.1 (built-in Kotlin), Kotlin 2.4.21, KSP 2.3.12, Compose BOM 2026.09.00, Room 2.8.5, Vico 3.3.1, MapLibre Native 13.7.1, Garmin FIT SDK 21.218.0, compileSdk/minSdk/targetSdk 37.

Issues in phase 0

Issue D1: the new SDK names things the old library did not

Symptom
13 of 45 FIT fixtures mismatched on first run, all in two fields: device (zepp Amazfit Bip 6 vs the PC's Amazfit Bip 6; nike 0 vs 326 0) and one sport (hiit vs the PC's 62).
Cause
The PC's fitparse bundles an older FIT profile. It returns a bare number for values it does not know, and the PC stored that string. The Garmin SDK knows Zepp, Nike and newer sports. The streams, laps and numbers all matched.
Solution
A script on the PC side (tools/export_fit_enums.py) exports fitparse's sport, manufacturer and Garmin-product tables, and the Kotlin parser looks names up there, including fitparse's rule that the product name is only resolved for manufacturers 1, 13 and 15. Result: 0 mismatches. Trade-off: new devices that fitparse never knew will also show as numbers, which keeps the two apps identical.

Issue D2: first charts drew nothing useful

Symptom
Axes and grid appeared, but the lines covered only the first 10 seconds; the heart-rate line spiked from 0 at the start; the pace panel was flat.
Cause
Vico draws 16 dp per point and scrolls by default, so a 2,724-point run extends far off screen. Missing samples were converted to 0, creating the spike.
Solution
Disable scrolling so the chart fits its content width; build each series from valid samples only and thin to about 500 plotted points (full data stays in memory for calculations); put the x-axis labels on a fixed fraction of the point count.

Issue D3: Vico 3 API differs from older examples

Symptom
Three compile errors (rememberLine, stacked) and deprecation warnings for lineSeries/columnSeries.
Cause
Version 3 moved rememberLine to an extension needing its own import, and renamed the stacking mode to MergeMode.Stacked.
Solution
Downloaded Vico's source jar and read the real signatures instead of guessing. Remaining warning: move to lineModel/columnModel in phase 1.

Issue D4: heatmap data took 24 s to build and froze the UI

Symptom
The Heatmap tab stayed blank for about 25 seconds (logged: build 24,062 ms).
Cause
The GeoJSON was assembled on the main thread with an object and several strings per point (140,886 points).
Solution
New Polyline.appendGeoJson in :core writes coordinates straight into one StringBuilder from integer maths, run on a worker thread; a unit test proves its output is character-identical to the plain decoder on every real route in the fixtures. Build time: 1,130 ms, main-thread hand-over 141 ms.

Issue D5: map tile prefetching conflicts with the OpenStreetMap policy

Symptom
Logcat showed MapLibre cancelling prefetched tile requests.
Cause
MapLibre prefetches neighbouring tiles by default; OSM's usage policy asks apps not to.
Solution
Prefetching turned off. Still to do in phase 4: send an identifying User-Agent for tile requests and verify it on the wire.

Issue D6: the emulator became unusable, then would not start (disk full)

Symptom
With the existing 2 GB virtual device, Android reported "Process system isn't responding" and the screen slept behind the dialog (screenshots came back black). After cloning the device with more RAM and an interruption, the emulator refused to start: "not enough disk space".
Cause
2 GB RAM is too little for Compose plus MapLibre on this image. My clone copied the whole 6.7 GB disk image (7.5 GB), leaving 1.5 GB free on the 237 GB disk.
Solution
Deleted only the clone I had made (the user's own device is untouched) and recreated "Pixel7 spike" from a configuration file alone (3 GB RAM, 4 cores, 4 GB data partition). Free space is about 4 GB. The PC's disk is nearly full; the user should free space before larger builds.

Issue D7: tooling traps while testing on the emulator

Symptom
Screenshots saved with PowerShell's > were not valid PNGs; am start sometimes did not switch tab; an instrumented test hung on "waiting for device" after the emulator exited; the first Android build reported 2 h 42 min.
Cause
PowerShell re-encodes redirected bytes as text; the app was already running; the emulator was a child of an interrupted session; the first build downloaded all dependencies (the elapsed time includes a long idle period, later builds take 4-52 s).
Solution
Take screenshots on the device and pull the file; force-stop the app before each launch and wait for the first frame; run gradlew --stop and restart the emulator when a device is lost; use JUnit 4's @Test in instrumented tests (kotlin.test.Test is not available there).

Finding D8: real data needs outlier handling on the pace chart

Observation
One GPS-start sample in the test run has an absurd pace, stretching the pace axis to 24:00 /km.
Plan
The activity page clips the pace axis to a robust range (for example the 2nd to 98th percentile) and the series to that range, and shows the raw values in the scrubber.

Finding D9: first start is slow on a cold emulator

Observation
On a freshly booted emulator the first frames took 15 to 30 s; later starts took about 3.6 s (am start -W). Debug builds are unoptimised.
Plan
Judge startup on the physical Pixel 7 with a release build and a baseline profile, not on the emulator.

Phase 0 is complete. Nothing found changes the architecture; two things change the design (streams as files; an ordinal duration axis) and one adds a requirement (a first-class theme system, below).

UI direction recorded 2026-10-17

The user asked for the app to look like Strava and to include a theme switcher with an iOS-style look and Unix-style themes. The design is in the "UI and themes" section above; it is built in phase 1 together with the import and list screens, so every screen is theme-aware from the start rather than retrofitted.

Phase 1: import and browse, with the theme system 2026-10-18

Goal: data in, then list and detail, with every screen theme-aware from the start. A Pixel 7 (Android 17, API 37) was connected over USB for this phase, so everything below ran on the real device rather than the emulator.

What was built. :core: GPX and TCX importers (an XmlPullParser element tree, tags matched by local name), moving time and the other helpers from the PC's importers/common.py, the FIT duration rule (device timer unless the track shows less movement), sport normalisation and the optional run/walk guess, the import pipeline (.gz, hash of the decompressed bytes, archive naming), route simplification (split at 250 m gaps, RDP at 5 m, encoded polyline), the gzipped stream file format, and display formatting with a units switch. :data: Room schema keyed by file_hash (activities, laps, routes, changes), a repository that archives the raw file, writes the streams file and inserts in one transaction, and an import runner that queues files off the main thread. :app: a FitnessTheme token set with eight theme families (Strava and iOS style with light and dark variants, Terminal green, Amber CRT, Solarized, Gruvbox, Nord, Dracula) mapped onto Material 3, themed components (card, section header, stat tile, segmented control, switch), the activity feed (date-range and sport filters, route thumbnails drawn on a canvas, long-press multi-select, delete with a typed DELETE for bulk), the detail screen (route map, stat tiles, heart-rate, pace and elevation charts whose scrubber moves a map marker, laps table), Settings (theme, light/dark, units, run/walk guess, street map), import by file picker and by share from another app.

Issues in phase 1

Issue E1: the app crashed on launch

Symptom
NullPointerException in the filter row on the first start on the phone.
Cause
The list of preset date ranges was a property of the sealed class's companion object. It was built while the subclasses were still initialising, so it held nulls.
Solution
Made it a function, called after everything is initialised. Found in the crash log with adb logcat -b crash.

Issue E2: the fixture's sha256_raw is the hash of the compressed file

Symptom
64 hash mismatches in the first parity run, all for .gz files; every other field matched.
Cause
The PC's file_hash is of the decompressed bytes (so x.fit and x.fit.gz are one activity), but the fixture field records the file as archived.
Solution
The test compares the first 12 characters of the hash with the archive name's prefix (what the PC derives from its own file_hash), and the full hash for uncompressed files.

Issue E3: the picker's Downloads root does not list files pushed with adb

Symptom
"No items" in the folder that adb push had filled.
Cause
That root is backed by the media index, which does not know files that were never scanned.
Solution
Browse through the "Pixel 7" storage root instead. Noted for the phase 3 seed transfer.

Issue E4: tooling traps

Symptom
One Gradle run failed in the Kotlin incremental cache (dirty-sources.txt); Git Bash turned /sdcard/... into a Windows path and could not see /tmp for the Windows adb; a test method written as = runBlocking { ... } was rejected by JUnit because it did not return void.
Solution
Delete core/build/kotlin and rerun; use MSYS_NO_PATHCONV=1 and Windows paths for adb; write runBlocking<Unit>.

Phase 1 is complete. Known gaps carried forward: elevation for the Amazfit runs is empty until the optional Strava CSV and terrain features (phase 7); the iOS theme's feed still uses separate cards, so its grouped-list structure shows most in Settings; labels are English only.

Phase 3: bulk import and rebuild 2026-10-18

Goal: get all 14 years onto the phone, unattended, and prove it matches the PC. The user chose to do this before phase 2, since it needs nothing from the analytics. First attempt: select all 3,265 files in the system file picker. It never reached the app (see issue F1), which is the reason the folder import below exists.

What was built. :core: same-run detection (Similar, a port of similar.py: moment, time-zone slip, same day; three modes) and a pure ImportPlanner that decides duplicate, same run or import, shared by the app and the JVM tests. :data: schema version 2 with an import_log table and a tested migration; FolderImporter (recursive walk of a folder the user picked, PC file order, Strava-export layout, a log row per file so a run can resume and a repeat run only looks at new files); rebuild from the archive (re-parse every original, keep identity and import date, deleted activities stay deleted); derived data (routes) rebuilt when missing or outdated at start-up; backup as a zip of the originals and restore through the normal import path. :app: a WorkManager foreground job (BulkWorker) for folder import, rebuild and restore with a progress notification and a Stop button, a preview before importing (file counts by format, how many an earlier run handled), an import-or-folder chooser, and Settings controls for the same-run mode, rebuild, backup, restore, forgetting the import history, and storage used.

(2) The run/walk guess is now on by default: an untyped activity is missing from every running analytic, and the PC's history was imported that way. (3) A repeat folder import only opens files whose size or date changed or that failed before; "Forget import history" in Settings makes it look at everything again. An activity the user deleted is not brought back by a repeat run. (4) A backup is the originals plus a small metadata file, not a database copy: the database is derived, so restoring reuses the normal import path and is idempotent. (5) The seed's pc-side-data.json (Strava CSV elevation, terrain elevation) is still not applied: it belongs to the optional phase 7 features.

Issue G3: opening a marathon from the records list crashed the app

Symptom
Tapping the Marathon row in Training, Curves and records closed the app.
Cause
The activity detail charts average many samples into each point for long activities, which gave times like 1234.3333; the chart library rejects x values with more than four decimals. Any activity of about 2 hours or more would have done it, from the feed too.
Solution
Chart times are rounded to whole seconds; a unit test covers a 15,000-sample activity. Checked on the phone with the marathon.
